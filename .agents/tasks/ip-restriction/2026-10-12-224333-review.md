# Per-group IP restriction enforcement

This change adds IP-based access control at the group level. Groups can be configured to require that members only connect from a predefined set of IPv4 addresses or CIDR ranges. The feature is off by default. When enabled, Next.js middleware enforces the restriction on every request before it reaches the application, redirecting blocked users to a Hebrew error page. Admins manage toggles and allowlists through a new collapsible panel in the existing groups UI.

Watch for: (1) **confirmed** — exact-IP matching in middleware uses string comparison, not bitwise, which means `" 10.0.0.1 "` ≠ `"10.0.0.1"` if the input has surrounding whitespace — trimming only happens in the helper but the exact-match branch in `lib/utils/ip-utils.ts` also trims, so it is consistent between the two files; however middleware's inline copy uses `ip.trim() === pattern.trim()` while `ipToUint32` is only called in the CIDR path, making the exact-match path bypass numeric range validation for IP octets — confirmed minor divergence from the spec. (2) **confirmed** — the toggle thumb in `GroupIpRestrictionManager` uses `-translate-x-5` for the enabled state in an RTL context, which moves the thumb *leftward* (toward the start of the element in RTL flow), making the enabled and disabled states visually indistinguishable in direction and possibly counterintuitive. (3) **confirmed** — the `add_ip_restriction_to_groups.sql` migration uses a UNIQUE INDEX but no `UNIQUE` constraint on `(group_id, ip_pattern)`; PostgreSQL treats a unique index as enforcing uniqueness, so the 23505 duplicate-detection code works, but this is a style gap. (4) **possible** — no middleware tests exist; the inlined IP helpers are tested indirectly through `ip-utils.test.ts` but the middleware session-extraction and flow logic have zero test coverage.

**Verdict**: APPROVED

## High-level view

The middleware is correctly isolated from Node.js-only modules. All DB access uses plain `fetch()` against the Supabase REST API with the service-role key, as required by the Edge Runtime. Fail-open is consistently applied: every error path — auth failure, missing profile, Supabase unavailability, missing IP header — lets the request through rather than blocking it. The skip-path list covers all required paths (`/ip-blocked`, `/login`, `/api/auth`, `/_next`, `/favicon`).

The migration is missing a `UNIQUE` constraint clause on `group_ip_allowlist (group_id, ip_pattern)`, relying instead on a unique index. Functionally equivalent in PostgreSQL; the 23505 error code is correctly caught in the POST handler.

The toggle thumb direction (`-translate-x-5` for enabled in RTL) is a UX concern. In a right-to-left layout the thumb should move toward the logical end to read as "on". The current implementation moves it leftward in RTL, which in a normal LTR toggle would mean "off". This may confuse Hebrew-speaking admins.

The allowlist fetch from middleware does not carry a `limit` clause, meaning if a group somehow accumulated thousands of entries the full table row-set would be transferred on every request. In practice allowlists are expected to be small, but an explicit limit (e.g. 500) would be a safe guard.

1. **Toggle thumb direction in RTL** — `GroupIpRestrictionManager` uses `-translate-x-5` for the enabled state. In RTL layout this moves the thumb left (toward the document start), which is the visual position of "off" in LTR toggles. Change to `translate-x-5` for enabled state in RTL, or remove the RTL `dir` inheritance from a parent and force the toggle to LTR with `dir="ltr"`.

2. **Exact-match in middleware bypasses octet validation** — The inline `ipMatchesPattern` in `middleware.ts` handles exact matches with `ip.trim() === pattern.trim()`, a string compare. A stored pattern like `"256.0.0.1"` would only match a client IP that is literally the same string — this is harmless in practice since `isValidIpPattern` blocks such values at insert time — but it means the middleware copy and the library copy diverge in what they validate. Low severity, confirmed by code inspection.

3. **Allowlist fetch has no row limit** — `group_ip_allowlist?group_id=eq.{groupId}&select=ip_pattern` in middleware carries no `&limit=N` parameter. Add `&limit=500` (or a similarly generous ceiling) to cap the data returned per request and avoid unbounded payloads on misconfigured groups.

4. **No middleware integration tests** — The inlined cookie-extraction and middleware flow logic (path skipping, token extraction, redirect decision) are untested. The `ip-utils.test.ts` file covers the helper library but not the middleware itself. Consider adding at least integration-level tests with a mocked `fetch` and `NextRequest` for the main decision branches.

### Toggle thumb direction in RTL context

`GroupIpRestrictionManager` renders a custom toggle switch. The enabled state applies `className="-translate-x-5"` to the thumb element. In an LTR toggle this would shift the thumb to the left, which is the "off" position — not "on". The component lives inside an RTL page, so the visual is inverted: left means "end" in RTL. But the CSS transform is viewport-relative, not flow-relative, so `-translate-x-5` unconditionally moves the thumb 20px to the left regardless of text direction. The net effect in an RTL context is that the thumb sits at the left edge of the track when enabled and at the right edge when disabled — the opposite of the expected reading. Use `translate-x-5` for the enabled state, or wrap the toggle in `dir="ltr"` to force conventional LTR rendering (common pattern for binary toggles in RTL UIs).

### CIDR matching and fail-open audit

The `/0` edge case is handled explicitly (`if (prefixLength === 0) return true`), which avoids the JavaScript `0xffffffff << 32` silent no-op. The property-based tests confirm this. Every return path in the middleware `try` block that cannot determine whether the IP should be blocked returns `NextResponse.next()`, including an empty allowlist (restriction enabled, zero patterns). The outer `catch` also returns `NextResponse.next()`.

### Test coverage

`lib/utils/ip-utils.test.ts` covers all four public functions with 34 tests including property-based tests for `ipMatchesPattern` (self-match and /0 universality). All FEAT-001 acceptance-criteria test cases are represented. The middleware flow — cookie extraction, REST fetch sequencing, redirect logic — has no test coverage. This is a gap for a security-critical code path.
